# Steering

Reference: `protocol/rust/src/steering.rs`. Mirrors: `protocol/kotlin/.../Steering.kt` (Android),
`protocol/swift/Sources/NineKit/Steering.swift` (iPhone). All three must reproduce
`protocol/vectors/steering.json` (tolerance 1e-6), generated by `cargo run -p nine-proto --bin gen-vectors`.

## Why the old method was wrong
The schema-1 method measured the angle of gravity in *screen* coordinates (`MotionMath.wheelAngleDeg`):
1. A player's natural tilted grip already read as a turn — the zero was "screen upright", not the grip.
2. Screen coordinates depend on the UI rotation, so a center saved on the portrait calibration screen
   was ~90° off on the landscape controller (seen on the device as −139°).
3. Tilted back beyond ~70° the angle was undefined and steering froze at its last value.

## Method
* Orientation as a unit quaternion q (body → world), from TYPE_GAME_ROTATION_VECTOR on Android
  (fallback TYPE_ROTATION_VECTOR, then gravity) and Core Motion device-motion attitude on iPhone.
  Body frame only; the display orientation is never an input.
* **Neutral** = the player's grip, held still ~1 s: mean quaternion after dropping samples beyond
  max(3σ, 1°). Accepted only if the RMS spread ≤ 1.5°.
* **Angle** = twist of r = q0*·q about the steering axis a (swing–twist), positive = right.
* **Axis**: default the screen normal (0, 0, −1). The wizard measures it from the held full-left and
  full-right poses (a = normalize(ρR − ρL)); the two turns must agree within 40°.
* **Output** = angle / (measured range on that side, or the layout lock) × sensitivity → invert →
  clamp → dead zone → curve. Left and right ranges are independent.
* **Filter**: One Euro on the angle (movement-adaptive: little lag on fast turns, steady at rest).
* **Recenter** (button, or once automatically when no calibration exists): never continuous. The
  output blends from the old reference to the new over 0.25 s, so the game never sees a step. Axis and
  ranges are kept (they are body-frame and relative); a grip change over 30° asks to re-measure.
* **Wrap**: unwrapped across ±180°, so turning past the end stays saturated instead of flipping.
* **Failure**: no sensor, unusable pose or invalid calibration → steering 0 (neutral), stated in the UI.

## Storage (schema 2)
`{"v":2,"kind":"orientation","q":[w,x,y,z],"axis":[x,y,z],"axisMeasured":true,"leftDeg":31,"rightDeg":28.5,"noiseDeg":0.4,"measuredAt":<epoch ms>,"source":"game rotation vector"}`.
Any other version, a missing/zero quaternion, one-sided range or a range outside 10…180° is rejected
as "not calibrated". Android stores it under `steering_cal_v2`; schema-1 keys are read only to tell
the player to measure again, and removed on the next save.

## Limits
* Game rotation vector heading drifts slowly; it only affects turns with a component about the
  vertical (recenter fixes it). Gravity-only phones cannot see a turn while the screen faces straight up.
* Verified: unit tests and cross-language vectors. **Not yet verified on a hand-held phone** — see the
  device test records under `tests/results/`.
